# Модель обработки ошибок KVS

## Иерархия исключений

Все исключения наследуются от `KvError` (который наследуется от `std::runtime_error`):

- `ParseError` — ошибка разбора команды (неверный синтаксис, неизвестная команда)
- `TypeMismatchError` — несоответствие типов (например, INCR для строки)
- `KeyNotFoundError` — обращение к несуществующему ключу
- `OutOfMemoryError` — нехватка памяти

Каждое исключение несёт контекст: имя ключа, ожидаемый и фактический тип.

## Граница обработки

**Правило:** Исключения ловятся ТОЛЬКО в одном месте — в цикле обработки команд в `kvs_cli` (файл `src/main.cpp`).

**Внутри `Store` и парсера ловить нельзя.** Там исключения только бросаются.

### Почему именно так?

1. **Единая точка обработки.** Все ошибки превращаются в ответ клиенту в одном месте. Это упрощает логирование и форматирование ответов.
2. **Чистая архитектура.** `Store` и парсер не знают о том, кто их вызывает (консоль, сеть, тесты). Они просто сообщают об ошибках через исключения.
3. **Безопасность.** Нет риска, что ошибка "проглочена" в глубине кода и программа продолжает работать с испорченным состоянием.

## Гарантии безопасности

- **Базовая гарантия:** нет утечек ресурсов, инварианты сохранены.
- **Строгая гарантия (для MSET):** либо все ключи записаны, либо ни одного. Реализовано через copy-and-swap.
- **noexcept:** деструкторы, move-операции и swap помечены как noexcept.

## Почему деструкторы noexcept?

С C++11 деструкторы неявно noexcept. Если деструктор бросит исключение во время раскрутки стека (когда другое исключение уже в полёте), программа немедленно завершится через `std::terminate()` без всякой очистки. Это катастрофа.

## Почему swap в MSET обязан быть noexcept?

В реализации `Store::mset` мы используем идиому copy-and-swap:
1. Создаём копию хранилища
2. Применяем все изменения к копии
3. Атомарно меняем местами оригинал и копию через `swap`

Если `swap` бросит исключение на шаге 3, сильная гарантия развалится:
- Мы уже подготовили новое состояние в `temp`
- Но не смогли атомарно его зафиксировать
- В результате и старое состояние уничтожено (при обмене), и новое не применено
- Объект остаётся в невалидном состоянии — это нарушение базовой гарантии

Поэтому `swap` ОБЯЗАН быть `noexcept`.

## Сравнение подходов: исключения vs std::expected

Мы реализовали два варианта функции парсинга:
- `parse()` — возвращает `Command`, бросает `ParseError` при ошибке
- `parse_expected()` — возвращает `std::expected<Command, ParseError>`

### 1. Читаемость вызывающего кода


**Исключения (`parse`):**
```cpp
try {
    auto cmd = parse(tokens);
    execute(cmd, store);
} catch (const ParseError& e) {
    std::cout << "ERR " << e.what() << "\n";
}

Читаемо: основной поток кода не загромождён обработкой ошибок.
Неявно: не видно из сигнатуры, что функция может бросить.

auto result = parse_expected(tokens);
if (result.has_value()) {
    execute(result.value(), store);
} else {
    std::cout << "ERR " << result.error().what() << "\n";
}

Явно: сигнатура говорит, что ошибка возможна.
Многословно: нужно проверять has_value() и вызывать value().
'

### 2. Стоимость при отсутствии ошибок

Исключения: В современных реализациях (zero-cost exceptions) накладные расходы на "счастливом пути" (когда ошибок нет) практически нулевые. Компилятор не генерирует проверок в обычном потоке выполнения.
std::expected: Всегда есть небольшая накладная стоимость: нужно проверить has_value() и, возможно, вызвать value(). Это сравнимо с проверкой std::optional.
Вывод: Исключения дешевле при отсутствии ошибок, но дороже при их наличии (раскрутка стека). std::expected имеет постоянную небольшую стоимость.


### 3. Поведение при прохождении ошибки через десять уровней вызовов
Исключения: Ошибка автоматически "всплывает" через все уровни вызовов, пока не будет поймана. Это удобно, но может привести к неожиданному поведению, если промежуточные функции не ожидали исключения.
std::expected: Каждую функцию нужно явно проверять и пробрасывать ошибку дальше:

auto result1 = func1();
if (!result1) return std::unexpected(result1.error());

auto result2 = func2(result1.value());
if (!result2) return std::unexpected(result2.error());

Это многословно, но явно показывает поток ошибок.
Вывод: Исключения удобнее для глубокой вложенности, но менее предсказуемы. std::expected требует явной обработки на каждом уровне, но даёт полный контроль.

Наш выбор: Мы используем исключения в основном коде, так как:
Граница обработки чётко определена (только в main.cpp)
Ошибки парсинга — исключительные ситуации, а не нормальный поток
Код чище и читаемее

## 5.1 Концепция Serializable

### Определение концепции

```cpp
template<typename T>
concept Serializable = requires(T t, const std::vector<std::byte> data) {
    { t.to_bytes() } -> std::convertible_to<std::vector<std::byte>>;
    { T::from_bytes(data) } -> std::same_as<T>;
};
